# 2Tamago : traductions (français et anglais)

L'interface existe en **français** (langue de référence) et en **anglais**. Ce document explique comment les textes sont organisés et comment en ajouter, pour que les dictionnaires restent cohérents.

## Principe

- **Le web possède tous les textes.** Le moteur (`shared/core`) et l'API n'envoient pas de phrases à afficher, mais des **codes** que le web traduit :
  - erreurs : le champ `code` (`GameErrorCode` du moteur, `ApiErrorCode` de l'API) donne la clé `error.<code>` ;
  - toasts de l'API : des `Notice` (`{ code, …paramètres }`, voir `shared/core/src/contracts`) ;
  - événements du compagnon et journal : des données (`PetEvent`, `ActivityDto`) mises en phrases par `web/src/lib/texts.ts`.
- Le champ `message` des erreurs de l'API reste une phrase **en français**, pour les clients non web et les journaux. Le web ne l'affiche que pour un code inconnu.
- Les noms des espèces (Mochi, Pyon…) sont des noms propres : ils restent dans le moteur (`SPECIES_LABELS`), identiques dans toutes les langues.
- Les titres des avis envoyés à GlitchTip (`[Bug] …`) restent en français : c'est la langue de l'équipe, pas celle du joueur.

## Organisation des fichiers

```
web/src/lib/i18n/
  index.svelte.ts        t(), translate(), langue courante, détection, pluriels
  i18n.spec.ts           tests du moteur de traduction
  locales.spec.ts        tests de structure des dictionnaires
  locales/
    fr/                  langue de référence
      index.ts           assemble les modules (export const fr)
      common.ts  shell.ts  catalog.ts  feed.ts  home.ts  minigame.ts
      adopt.ts  profile.ts  social.ts  shop.ts  auth.ts  admin.ts  feedback.ts  errors.ts
```

## Conventions de clés

- **`espace.élément`**, en minuscules et `snake_case` : `home.egg_hint`, `feedback.type.bug_hint`. La clé complète est écrite dans le dictionnaire (pas d'imbrication) : chercher une clé dans le dépôt trouve sa définition et ses usages.
- **Pluriels** : deux clés `…_one` et `…_other`, avec un paramètre `{count}`, appelées sans suffixe : `t('notice.coins_earned', { count })`. La catégorie vient d'`Intl.PluralRules` (en français, 0 est au singulier).
- **Paramètres** : `{nom}`, les mêmes dans toutes les langues. Passer les valeurs déjà traduites (`itemLabel(id)`), pas des identifiants.
- **Clés dynamiques** : `t(\`stage.${stage}\`)`est typé. Une clé bâtie depuis des données externes (un code d'erreur) se vérifie d'abord avec`hasMessage`.
- **Un texte = une clé.** Ne pas réutiliser une clé pour un autre sens, même si le français est identique (`feedback.title` sert au bouton et au titre de la modale, car c'est le même texte).
- Les emojis qui font partie d'un libellé de bouton sont dans le texte traduit (`action.feed` : `🍙 Nourrir`).

## Écrire un texte dans un composant

```svelte
<script lang="ts">
  import { t } from '#lib/i18n/index.svelte.ts';
</script>

<h1>{t('shop.title')}</h1><p>{t('shop.in_bag', { count })}</p>
```

`t()` lit la langue courante (un `$state`) : tout ce qui l'appelle dans un gabarit ou un `$derived` se met à jour au changement de langue. Les constantes de module ne doivent donc pas contenir de texte traduit : stocker la **clé** (`label: 'nav.home'`, typée `MessageKey`) et appeler `t()` à l'affichage. Les formats de date et de nombre passent par `Intl` avec `intlTag()` (`fr-FR` ou `en-GB`).

Les toasts sont traduits au moment où ils sont créés : ils ne changent pas si on change de langue pendant qu'ils sont affichés.

## Ajouter une clé

1. Choisir le module (voir le tableau) et ajouter la clé dans `locales/fr/<module>.ts`.
2. Ajouter la même clé dans `locales/en/<module>.ts`. Le typage (`Record<keyof typeof fr, string>`) refuse le fichier tant qu'il manque une clé ou qu'il y en a une en trop, avec une erreur dans le bon fichier.
3. Utiliser `t('espace.élément')` : TypeScript refuse une clé qui n'existe pas.

Pour un nouvel espace de noms ou un nouveau module : l'ajouter au registre `NAMESPACES` de `locales.spec.ts`, créer le fichier dans chaque langue et l'assembler dans les deux `index.ts`.

Pour un nouveau **code d'erreur** (moteur ou API) : l'ajouter à `GAME_ERROR_CODES` ou à `API_ERROR_CODES` (`shared/core`), puis écrire `error.<code>` dans les deux langues. Des tests refusent un code sans message.

## Ajouter une langue

1. Ajouter son code à `LOCALES` et son étiquette `Intl` à `INTL_TAGS` (`index.svelte.ts`), et le nom de la langue (`lang.<code>`) dans `common.ts` de chaque langue.
2. Copier `locales/en/` vers `locales/<code>/`, traduire, et déclarer la langue dans `DICTIONARIES`.
3. Le sélecteur de l'en-tête alterne aujourd'hui entre deux langues : en prévoir un menu à partir de trois.

## Choix de la langue

Priorité : choix enregistré (`localStorage`, clé `locale`), puis langue du navigateur (`navigator.languages`), puis anglais. `<html lang>` suit la langue courante. Le bouton « FR / EN » de l'en-tête (et de l'écran de connexion) bascule et mémorise le choix.

## Garde-fous

`locales.spec.ts` vérifie, pour chaque langue : les mêmes modules et les mêmes clés que le français, des clés à la bonne forme et dans le bon espace de noms, aucune clé définie deux fois, les mêmes paramètres, des pluriels complets, aucun texte vide, un message pour chaque code d'erreur, et **aucune clé inutilisée** dans le code de l'application. `api/src/common/error-codes.spec.ts` vérifie que tout code envoyé par l'API est déclaré. Le test Playwright `language.spec.ts` couvre la détection, la bascule et la mémorisation. Les tests Playwright fixent la langue du navigateur en français (`playwright.config.ts`).
